# Design

## Context

動機與產品範圍見 [proposal.md](proposal.md)，行為契約見 [desktop-task-management](specs/desktop-task-management/spec.md)。本次同時涉及持久化狀態、共用服務與 SwiftUI，且需處理分頁及移除時的執行競爭，因此建立設計文件。

已查證的現況：

- `database.py` 已有 `batches`、`jobs`、`attempts`、`events` 與安全重送用的 `requests`；批次有 `created` 與 JSON `details`，任務已有 `batch_id`。
- `workspace.py` 的每次 `submit` 已建立批次；`jobs.list` 只支援批次及分頁，`counts` 已依 `batch_id` 統計，未指定批次時為全域統計。`jobs.retry` 依單一任務／批次 ID 重試失敗、取消、中斷任務，來源驗證失敗會整筆交易回滾。
- `DesktopView.swift` 每次載入 100 筆任務，以單一選取顯示詳情；既有輸出按鈕直接開啟 `output_dir`。
- `intake.py` 的 `probe` 已使用內建 FFprobe 取得有限正值的媒體時長，預覽項目與接受後的任務均保存 `duration_ms`；但 GUI 沒有顯示。現有完整預覽還要求輸出目錄與辨識設定，並讀取完整來源指紋，不適合直接當作選檔後的輕量時長讀取。
- `scheduler.py` 在同一協調程序依序領取任務；執行回收以 attempt 及程序群組為準。尚未完成回收前不能刪除它所需的資料列。
- `exports.py` 在 `jobs/<job-id>/outputs.json` 保存逐檔交付紀錄，包含失敗前已提交的部分成果；只有預定 `outputs` 路徑不能證明成果已交付。完整成功的 worker 結果另帶 `outputs_ledger`，但列表刻意不回傳整份 ledger。
- `add-macos-desktop-batch-transcription` 已於 2026-10-24 同步規格並封存，桌面生命週期契約沿用其主規格。本變更以現有程式為基礎，新增獨立管理能力，不將其要求再宣告一次；未完成的安裝／簽署驗收也不列為本變更已完成事項。

## Goals / Non-Goals

**Goals:**

- 所有查詢與修改仍由單一協調程序維護權威狀態，GUI 不直接讀寫 SQLite。
- 搜尋、結果筆數、多選與操作共用相同範圍定義，避免只處理當頁或誤操作隱藏任務。
- 以既有資料欄位及交易機制完成名稱保存和紀錄移除，不引入額外儲存服務。

**Non-Goals:**

- 不增加批次合併、任務搬移、標籤、人工優先順序、任意排序或自動重試。
- 不刪除來源、成果、工作目錄、媒體快取、checkpoint 或日誌，不承諾移除紀錄能回收磁碟空間。
- 不提供復原／垃圾桶，也不將移除紀錄視為抹除日誌、事件及請求紀錄中的所有歷史痕跡。
- 不新增 CLI 命令族或 Finder 命令；這次以 GUI 操作與共用協定為範圍，既有 CLI 維持可用。

## Decisions

### 1. 沿用批次 ID，以現有 details 保存名稱

`batches.details` 新增可選的 `name`，沒有名稱的既有批次使用同一個服務端函式，依原 `created` 與第一個有效來源的檔名產生預設名稱。服務端以使用者本地時區產生時間文字及可搜尋名稱，GUI 直接使用所回傳的名稱，避免列表與搜尋各自推導不同名稱。批次總數獨立顯示，不把會變動的剩餘數量寫入名稱。

名稱去除首尾空白後須為 1–100 個 Unicode code point；以服務端結果為準，GUI 的字數提示使用相同計數規則。允許同名，批次 ID 才是身份。保存名稱時合併現有 `details`，不可覆蓋提交計畫。使用現有 JSON 欄位不需增加 schema 版本或重分組舊任務。

新增 `batches.list` 與 `batches.rename`，列表以 `created DESC,id` 穩定分頁，回傳名稱、建立時間、各狀態數量與總數。使用既有批次 ID 的改名比以可變名稱當 key 更可靠；不採用「依日期重新推測批次」。

### 2. 在服務端先套用共用條件，再分頁與統計

`jobs.list` 增加可選 `query` 與 `states`，保留 `batch_id`、`offset`、`limit`。空白搜尋等同無文字條件，空的狀態陣列等同全部狀態；多個狀態取聯集，再與範圍、文字條件取交集。狀態使用既有八種值，未知值或不合法型別明確拒絕。文字以檔名或有效批次名稱作字面包含比對，至少忽略英文大小寫；百分號、底線及引號不具有特殊意義。

資料層集中同一份條件解析與目標解析，供列表、結果計數、全選及操作使用。以 SQLite 綁定參數查詢現有 JSON 中的來源／名稱，必要的檔名提取與文字正規化共用同一純函式並可註冊為 SQLite 查詢函式；條件在 `LIMIT/OFFSET` 前生效。避免逐筆載入完整 `db.job` 後再篩選，也不為此引入全文搜尋或額外搜尋資料庫。

回應新增 `scope_counts`（目前批次或全部任務、尚未套文字／狀態）與 `matched_counts`（完整篩選結果）；`total` 是符合結果筆數。原有 `counts` 的批次範圍語意保留：指定 `batch_id` 時統計該批，未指定時統計全部任務，皆不受新增文字／狀態條件影響，GUI 改用新欄位並明確標示。舊呼叫未提供新條件時，排序、分頁及既有欄位行為不變。

選擇服務端過濾是為了涵蓋所有分頁；不採用只篩目前 `model.jobs` 的方式。搜尋只處理必要 metadata，不讀音訊、不做來源指紋計算。

### 3. 批次、列表與詳情分欄，多選以穩定 ID 表示

任務頁採批次導覽、任務列表與詳情三區；保留全部任務入口。搜尋與狀態選擇位於列表上方，範圍摘要常駐顯示，批次選單提供改名、重試此批失敗任務、移除此批全部任務紀錄。

任務列不再使用陣列 offset 作為 SwiftUI 身份，改用 job ID；多選與檢視詳情分開，避免選取多筆時任意顯示錯誤詳情。同一查詢換頁保留已選 ID，切換批次或條件則清空多選及重設 offset。全選符合結果保存查詢範圍與目標版本，而非只保存目前頁面；換頁不改變其含義。

搜尋輸入採短暫 debounce，查詢帶本地 generation；只有仍符合當前條件及 generation 的回應才能更新畫面。既有刷新中的保護不能吞掉新搜尋，需在完成後執行最新待處理查詢。改名、重試、移除後重查批次與任務，修正超界頁碼，清除已不存在或已不符合條件的選取。

相較於只在平面列表插入可折疊批次，獨立導覽能同時保留跨批次搜尋與穩定的整批操作入口。此為介面結構決策，不新增任務分類系統。

### 4. 明確選擇器與可重送的多筆操作

新增操作接受兩種互斥 `selector`：明確 `ids`，或查詢範圍（可選 `batch_id`、`query`、`states`）。整批入口只傳 `batch_id`；選取入口傳明確 ID 或全選結果的範圍。單筆是只有一個 ID 的選取，不另建一套行為。

沿用 `jobs.retry`，保留原有 `id` 參數的完整相容語意；新增 `selector` 及 `failed_only`，不可與舊 `id` 混用。「重試此批失敗任務」以整批 selector 加 `failed_only=true` 執行；一般選取則允許 failed／cancelled／interrupted。先驗證整個合法目標的來源，再原子更新；來源遺失或變更時回傳具體任務與原因，不留下部分重試。回應顯示實際重試數與因狀態略過的數量／原因，沒有符合項目時明確說明。

全選符合結果的重試另外帶選取時取得的 `target_token`，在交易內檢查集合與狀態；版本不同時要求更新選取，不讓新符合的任務自動加入。單筆／明確 ID 選取依目前狀態篩選合法重試項目；整批失敗入口則以操作當下該批所有失敗任務為範圍。

新增 mutation 全部使用 `Database.command` 的交易與安全重送；GUI 為一次操作產生並保存 request ID，回應遺失的重送須帶同一 ID。不同的下一次操作才產生新 ID。來源驗證可能超過現有一般 socket 的 3 秒期限，Swift 對批次重試需採與長操作相容的 timeout，且不能因 timeout 自動換 ID 重做。

大量全選由服務端 selector 解析，避免將所有 ID 塞入 64 KiB 請求；明確 ID 選取若超過傳輸上限，提示縮小選取，不默默截斷或拆成無法原子處理的多次移除。

### 5. 移除採唯讀預覽與交易內再驗證

新增唯讀 `jobs.selection.preview`，解析 selector，回傳範圍摘要、總數、狀態數量、可重試數、不可移除原因與 `target_token`，供全選與移除確認共用。token 為正規化條件、排序後目標 ID／state／attempt ID 的摘要，不需另外保存預覽資料表。全選時即保存 token，之後的移除預覽須與原 token 一致；實際操作若集合或狀態改變，要求重新選取及確認，不靜默帶入新增符合項目。

GUI 以預覽數量與批次名稱顯示確認，固定文案說明「原始影音檔與已產生的 TXT、SRT、JSON 成果都會保留。移除後，無法從原任務查看詳情或重試。」文字依選取／整批替換，確認按鈕包含實際筆數；另說明此操作不清理快取或釋放成果空間。

`jobs.remove` 帶 selector 及 target token，在 `Database.command` 交易內重新解析並核對 token、任務狀態及執行中的 attempt。任何目標是 running、cancelling 或仍有未回收 attempt，整次拒絕。前端不以按鈕 disabled 代替服務端檢查，也不提供隱式「先取消再移除」。取消後等待停止，由使用者重新確認。

queued／blocked 任務可在同一交易直接移除，之後排程查詢不會再領取；completed／failed／cancelled 及完成回收的 interrupted 亦可移除。依外鍵先移除相關 attempts，再移除 jobs，批次已無任務時才移除 batches。成功寫入帶目標 ID 的移除事件；保留既有 requests 重送紀錄，原 submit 的重送只回放原結果而不復活任務。舊事件可保留為歷史，但最新列表／詳情／snapshot 始終以現存資料列為準。

採用資料列移除而非新增軟刪除狀態，可避免排程、模型引用與每個舊查詢都必須新增隱藏條件。此操作完全不呼叫檔案刪除；保留的交付 ledger 仍可辨認原成果，不保證新提交可無條件接管舊成果。沒有 overwrite 授權時，既有輸出衝突規則繼續生效。

### 6. Finder 使用檔案 URL 與已交付成果摘要

共用服務提供單筆任務的精簡 `delivered_outputs` 摘要，依既有交付 ledger 中 committed 的紀錄與檔案存在狀態產生，另回傳尚未交付與已交付後遺失的格式，讓 GUI 區分兩種原因。從 `jobs.show`／必要的詳情查詢取得，避免每次重整 100 筆清單就讀全部 ledger 或重新計算檔案雜湊。部分匯出失敗時仍讀得到已交付格式；沒有 ledger 的舊成功任務，可依 completed 狀態及預定輸出的存在狀態提供相容摘要。

Swift 以檔案 URL 與 `NSWorkspace` 的 Finder reveal 能力定位，不拼接 shell 指令。原始檔選取來源 URL；同資料夾的多格式成果一起選取，若未來存在不同成果資料夾則按格式提供入口，不任意開根目錄。任務列右鍵與詳情共用相同位置動作。

操作時再次確認路徑是否存在並處理 Finder 開啟結果。無成果、成果已遺失及開啟失敗使用不同說明；不建立缺少的資料夾，也不自動退到與成果無關的位置。提交計畫中的 `outputs` 繼續顯示為預定路徑，不直接當成已交付證據。

### 7. 以附加協定能力維持相容

協定仍為版本 1，新增操作納入 `OPERATIONS` 及 `service.status` 現有 capability 清單，既有呼叫的必填欄位及語意不變。新 GUI 連到缺少本次能力的舊 helper 時提示重新啟動相同版本服務，不在舊服務上送出會被忽略的搜尋參數，避免錯把未篩選列表當作搜尋結果。

`batches.rename`、擴充 retry、`jobs.remove` 的事件促使其他客戶端重新讀取權威狀態；已刪任務詳情回報 not_found。CLI 不新增命令，但原有 jobs list/show/retry/cancel/watch 與 request ID 回放須回歸驗證。既有 `counts` 保留批次範圍統計語意，避免撤回先前已驗證的批次統計修正；新 GUI 使用 `scope_counts` 與 `matched_counts` 區分範圍和篩選結果。

### 8. 加入來源即背景讀取時長，提交後沿用已保存數值

選檔、拖放、來源清除與遞迴設定變動共用來源清單更新入口；檔案加入後立即呈現讀取中，再於背景探測。新增唯讀 `intake.inspect` 及其 capability，只需來源路徑與遞迴設定，不需要模型或輸出目錄，也不建立 batch／job。資料夾發現、重疊來源去重、符號連結排除與既有 intake 規則一致，重用現有 FFprobe 與 `probe` 的時長定義，不新增媒體解析依賴、不跑 ASR 或完整來源雜湊。

探測使用有上限的背景工作及既有單檔 timeout，不讓大量檔案探測長時間阻塞 SwiftUI 主執行緒或協調程序排程／控制。背景工作只處理唯讀媒體資訊，不直接存取 SQLite；來源檢查結果依檔案分別呈現成功或錯誤。一個不可讀檔案不終止其餘檔案讀取。此來源檢查的進行中狀態是匯入表單狀態，不加入原有八種轉錄任務狀態。

表單保存來源清單的 generation 及每檔探測結果，清除或變更遞迴範圍後丟棄過期結果；變更輸出格式／目錄或重畫畫面不重讀已知時長。若來源重新加入或檔案資訊已改變則重新探測，不使用長期持久化的時長快取。正式預覽與提交仍照原契約重驗媒體與來源，成功提交的 `duration_ms` 才是該任務保存的數值，不能以先前的輕量結果省略來源驗證。

共用一份時長格式化規則：以毫秒保存，介面向下取整至秒，未滿一小時顯示 `m:ss`，一小時以上顯示 `h:mm:ss`，已知正值但未滿一秒顯示「小於 1 秒」。讀取失敗顯示個別原因，缺少數值顯示未知，不以 `00:00` 代替。匯入清單、正式預覽、任務列及詳情使用同樣規則；任務列與詳情直接讀已保存的 `duration_ms`，不因刷新列表重新探測。媒體時長只描述來源內容長度，不加入處理速度估算、批次總時長或時長排序／篩選。

## Risks / Trade-offs

- [確認期間排程開始執行或有其他客戶端操作] → 移除以目標 token 與交易內狀態／attempt 檢查全有全無；狀態改變重新確認。
- [大量任務搜尋與批次計數拖慢單一協調程序] → 僅查詢必要 metadata、在分頁前篩選並避免完整 job／ledger 逐筆載入；用超過一頁及多批次資料驗證正確性並記錄查詢耗時，沒有實測不承諾固定延遲或先加全文索引。
- [來源位於慢速磁碟導致重試驗證時間較長] → 保存操作 request ID、使用適當 timeout 及操作中狀態；本變更改善定位與批次操作，不跳過來源內容校驗。
- [大量或無法回應的來源令時長探測延遲] → 使用有上限的背景探測與逐檔 timeout，讀取中／個別錯誤持續可見，來源清單變動後忽略過期結果，不能拖住既有佇列控制。
- [移除紀錄被誤解為刪除檔案或釋放空間] → 功能名稱、確認視窗及使用文件一致說明保留來源、成果與快取，並明示失去原任務入口。
- [既有事件／請求回放含已移除任務 ID] → 查詢與刷新以現存資料列為準，移除事件不復活資料，保留安全重送結果但不重新執行 submit。
- [同名批次、中文／空白路徑或 Finder 路徑競爭] → 用 ID 作身份、名稱搭配提交時間顯示、採檔案 URL 並處理操作當下的路徑失效。
- [與原始桌面規格的關係] → 本提案以獨立能力補充現有行為，實作／封存前核對兩個變更的規格關係；不改動或代勾原變更任務。

## Migration Plan

1. 先在暫存 workspace 以既有 schema 資料驗證新批次列表、名稱 fallback 與查詢；沒有 `name` 的批次不需資料遷移，首次改名僅更新其 `details`。
2. 先完成服務端操作、回放與相容性測試，再接 GUI；更新 App 與 helper 後以 capability 檢查避免新舊能力混用。
3. 以隔離的測試檔與至少兩批、超過 100 筆混合狀態任務驗收加入時讀取時長、搜尋、多選、範圍文案、改名持久化及移除保留檔案；另以受控 worker 驗證取消／回收競爭。
4. 完成原生測試與建置、相關 Python 回歸及實際 Finder 入口檢查後，更新協定和使用說明，記錄本變更驗收證據。沒有實際執行的驗收維持未完成，不以規格驗證代替功能驗證。
5. 回退程式可繼續讀取舊結構與新增名稱欄位；已移除的資料列不會因程式回退自動復原。回退不是復原機制，若需還原必須使用操作前完整 workspace 備份；來源、成果與快取仍保留。
